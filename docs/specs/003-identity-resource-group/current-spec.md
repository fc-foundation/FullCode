# Identity Resource Group

Status: done

## Problem

GitHub Actions pipelines need to authenticate to Azure to run Terraform (plan today, apply eventually), but there is currently no Azure identity or trust relationship for this repo's CI to use. Without OIDC federation, the pipeline would need a long-lived client secret stored in GitHub, which carries ongoing rotation burden and a larger blast radius if leaked.

## Goals

- A manual (human-run) PowerShell script that provisions, per environment (`dev`, `test`, `prod`):
  - A dedicated resource group to hold identity resources, separate from workload resource groups.
  - A user-assigned managed identity (UAMI) in that resource group.
  - A federated identity credential on that UAMI trusting GitHub Actions OIDC tokens for this repo, so the pipeline authenticates without a stored secret.
- The script is parameterized by environment so it can be re-run per environment rather than hardcoded to one.
- Resource and identity names follow this repo's existing CAF-based naming convention (`infra/terraform/modules/naming`).
- The script is idempotent — safe to re-run against an already-bootstrapped environment without failing or duplicating resources.

## Non-goals

- Automating this via Terraform/CI — intentionally a manual bootstrap script, since Terraform's own pipeline identity can't be created by Terraform before that identity exists (chicken-and-egg).
- Managing the GitHub Actions workflow YAML that consumes this identity — separate concern; this spec only produces the Azure-side identity and its federation.
- Fine-grained/least-privilege custom RBAC role definitions — see Open questions for the assumed role.

## Requirements

1. **PowerShell, manual execution.** The script uses Azure PowerShell (`Az` module) cmdlets and is intended to be run manually by an operator, not invoked from CI.
2. **Per-environment parameterization.** The script accepts a mandatory `-Environment` parameter restricted to `dev`, `test`, or `prod` (matching the existing naming convention's supported environments), a mandatory `-Workload` token, and derives all resource names from them. Every parameter is mandatory (no defaults) so an operator must explicitly choose every naming input rather than silently inherit one; `-Location` is further restricted via `ValidateSet` to the regions in `infra/terraform/modules/naming/locals.tf`'s `region_abbreviations` map.
3. **Identity resource group.** For the given environment, the script creates (or confirms) a resource group dedicated to identity resources, named per the CAF convention.
4. **User-assigned managed identity.** The script creates a user-assigned managed identity inside that resource group.
5. **GitHub OIDC federation.** The script creates a federated identity credential on the managed identity trusting `https://token.actions.githubusercontent.com` as issuer, audience `api://AzureADTokenExchange`, and a subject scoped to this repo (`fc-foundation/FullCode`) and the given environment. The credential's own name is `<GithubFederationName>-<Environment>`, where `-GithubFederationName` is a mandatory parameter (no default).
6. **RBAC assignment.** The script assigns the managed identity a role sufficient for Terraform to deploy the environment's resources (see Open questions for exact role/scope).
7. **Idempotency.** Re-running the script for an already-provisioned environment does not fail or create duplicate resources — it detects existing resources and confirms or updates them in place.
8. **Output for pipeline configuration.** The script outputs (console and file, both required) the values needed to configure the GitHub Actions workflow: the managed identity's client ID, tenant ID, and subscription ID.

## Open questions

- **RBAC scope/role**: assuming Contributor scoped to the subscription, since Terraform will eventually create resource groups and resources across the subscription (network foundation, etc.) rather than one fixed resource group. Revisit toward a narrower scope once real workloads exist and the actual resource footprint is known.
- **Federated credential trust subject**: subject is `repo:fc-foundation@312288273/FullCode@1358339302:environment:<environment>` (GitHub's immutable-ID subject form; see Implementation notes) for all three environments, tying federation to GitHub Environments named `dev`/`test`/`prod`. This is deliberately branch-agnostic — GitHub only emits the `environment:` form when the workflow job sets `environment: <name>`, so which branch(es) may deploy to a given environment (e.g. a feature branch deploying to `dev`) is controlled entirely by that GitHub Environment's "Deployment branches and tags" protection rule, not by anything in this script or the Azure-side subject. This also enables required-reviewer approval gates on `prod` via the same protection-rule mechanism. Creating those three GitHub Environments in repo Settings is a manual follow-up outside this script (done — see Implementation notes).
- **Identity resource group naming — resolved.** Rather than one shared reserved instance value for both the resource group and the identity, the script takes two separate mandatory parameters, `-ResourceGroupInstance` and `-IdentityInstance`. They're allowed to be equal — the `rg-`/`id-` resource-type prefix already keeps the two resulting names distinct, so no additional guard is needed. `.local/Invoke-IdentityResourceGroup.ps1` currently passes `000` for both, a 3-digit number matching `infra/policy/naming.rego`'s `standard_pattern`'s `[0-9]{3}` instance segment (`rg-fc-dev-eus2-000`). Two earlier attempts didn't work: non-numeric instance values (`iam`/`gh`) failed the instance segment's `[0-9]{3}` regex, and folding `iam` into the workload segment (`fciam`) failed because `naming.rego`'s workload segment is a literal `fc`, not a variable, so nothing but `fc` itself can appear there.
- **Region scope — resolved, broader than originally assumed**: `-Location` now supports all Azure public-cloud US regions (`eastus`, `eastus2`, `centralus`, `northcentralus`, `southcentralus`, `westcentralus`, `westus`, `westus2`, `westus3`), mirroring `infra/terraform/modules/naming/locals.tf`'s `region_abbreviations` map (also expanded from `eastus2`-only during this work), rather than being hardcoded to `eastus2`.
- **Subscription scope**: assuming a single Azure subscription hosts `dev`/`test`/`prod`, distinguished by resource group naming only. `-SubscriptionId` is a mandatory parameter (no longer defaults to the current `Az` context), so a per-environment subscription is already supported by passing a different value per run if that assumption changes.
- Should PR-triggered `plan`/`validate` jobs get their own more restricted, separately-federated identity (read-only) distinct from the apply-capable environment identity? Assuming out of scope for now — can be added later as its own federated credential if needed.

## Implementation notes

- `scripts/New-IdentityResourceGroup.ps1` implements all 8 requirements: `-Workload`/`-Environment` (`dev`/`test`/`prod`) parameterization (all parameters mandatory, no defaults), idempotent (check-before-create, and update-in-place for a drifted federated credential) resource group + user-assigned managed identity + federated credential + subscription-scoped Contributor role assignment, and a final object (plus required `-OutputPath` JSON) with the client ID, tenant ID, and subscription ID needed for the GitHub Actions workflow.
- Naming replicates the relevant slice of `infra/terraform/modules/naming/locals.tf` by hand via a `Get-RegionAbbreviation` function (all 9 US region abbreviations, workload taken from the mandatory `-Workload` parameter rather than hardcoded) since that Terraform module can't be called from a standalone script — commented in the script as needing to stay in sync, same precedent as `infra/policy/naming.rego`. Resource group and identity use separate mandatory `-ResourceGroupInstance`/`-IdentityInstance` values (currently `000`/`000` via `.local/Invoke-IdentityResourceGroup.ps1`) to distinguish them from workload instances; they don't need to differ from each other, since the `rg-`/`id-` prefix already keeps the two names apart — see the Open questions entry.
- Role assignment retries briefly (5 attempts, 10s apart) to absorb Azure AD replication lag for a freshly created identity's service principal — a real `New-AzRoleAssignment` failure mode, not speculative.
- **GitHub sign-in on Windows PowerShell 5.1**: `Connect-AzAccount`'s default WAM (Web Account Manager) broker can throw `Method 'get_SerializationSettings' ... does not have an implementation` under Windows PowerShell 5.1 (no per-module assembly isolation, unlike PowerShell 7), and separately can render a blank account picker. `.local/Invoke-IdentityResourceGroup.ps1` works around the blank picker with `Connect-AzAccount -UseDeviceAuthentication`; installing and running under PowerShell 7 (`pwsh`) is the more durable fix for the assembly-mismatch error.
- **Verified end-to-end**: the operator ran `.local/Invoke-IdentityResourceGroup.ps1` against the live `dev` subscription and it completed successfully, creating resource group `rg-fc-dev-eus2-000`, managed identity `id-fc-dev-eus2-000`, its federated credential, and the Contributor role assignment. Output was captured to `.local/Github-Federated-Identities/dev-identity.json` (client ID `91337d9a-0901-42c1-b987-173bdb12c621`, tenant `953238b7-3d31-490f-86c0-7e81a3a9502d`, subscription `a897c71d-73a0-4b90-b084-9d2b39eee4eb`). This is the first real confirmation of the script beyond static parsing, so Status moves to `done`. `test`/`prod` have not been run yet — re-run the same script with `-Environment test`/`-Environment prod` (and the corresponding GitHub Environment/branch policy already in place) when those are needed.
- **GitHub Environments created**: `dev`, `test`, and `prod` now exist in the repo's Settings > Environments (created directly via the GitHub API, not by the script), so the federated credential's subject (`repo:fc-foundation@312288273/FullCode@1358339302:environment:<environment>` (GitHub's immutable-ID subject form; see Implementation notes)) matches pipeline runs. No protection rules were added to any of them — the org (`fc-foundation`) has exactly one member (`EdwardRushDeveloper`), so a required-reviewer gate on `prod` would just be a self-approval, which can stall solo deploys depending on repo settings. Revisit adding a reviewer rule on `prod` if/when a second org member exists.
- **Naming module gap (informational, not a blocker)**: `infra/terraform/modules/naming/locals.tf`'s `resource_types` map has no entry for a user-assigned identity, so the script's `id-` prefix is hand-picked rather than validated against that module. Out of scope for this spec (that map belongs to `001-infrastructure-naming`), but worth reconciling there if a formal identity resource type is ever added to the naming convention.
- **Federated subject changed to the immutable-ID form (found by `004-terraform`).** The first real OIDC sign-in, the `Terraform Deploy` PR run on PR #5, failed with `AADSTS700213: No matching federated identity record found for presented assertion subject 'repo:fc-foundation@312288273/FullCode@1358339302:environment:dev'`.
  - Cause: the repo's OIDC subject setting (`gh api repos/fc-foundation/FullCode/actions/oidc/customization/sub`) has `use_immutable_subject: true`. GitHub therefore embeds the numeric owner and repo IDs in the subject, and the name-only subject this script originally built never matched.
  - Script fix: `New-IdentityResourceGroup.ps1` now takes two more mandatory parameters, `-RepositoryOwnerId` and `-RepositoryId` (digits only), and builds `repo:<owner>@<ownerId>/<repo>@<repoId>:environment:<env>`. `.local/Invoke-IdentityResourceGroup.ps1` passes `312288273` / `1358339302`.
  - Live fix: `dev`'s credential `github-actions-dev` was updated in place with `az identity federated-credential update` (no re-run needed). A re-run of the script now reports "already matches".
  - This form was kept deliberately instead of turning `use_immutable_subject` off, because it keeps the trust safe if the org or repo is renamed or the name is re-registered.
